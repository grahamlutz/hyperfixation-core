## Corrections this pass produced

1. **Telegram is half built.** Phase 2 shipped the decoder and `decideFromCallback`; F2 ships only what sends and links.
2. **"Channels (email)" is done except inbound**, and inbound cannot be SMTP: the box has no MX and Hetzner blocks
   465. Inbound-by-reply-code needs Cloudflare Email Routing → a Worker → the app's webhook — a surface outside both
   repos. **Deferred by decision;** nothing in Phase 7's Done-means needs it.
3. **Cadences need no table.** The plan's Phase 6 row has no `hf_cadence`, and none is needed: a touch is an
   `hf_action_log` row with `(record_type, record_id, key = '<cadence>:<touch>')`, so "what went and when" is a query
   and the tick derives what is due. The key shape joins the key-derivation snapshot (contract, per the policy).
4. **The `embedding` column has no writer** without a ledger path, and the only embedding provider on the cost table
   is OpenAI. `llm.embed` is a Phase 6 addition to `@hyperfixation/ai`, and `demo-two` needs an OpenAI key.
5. **One Telegram bot has one webhook URL**, so it is one bot per app, provisioned like a Sentry project.
6. **Four follow-ups belong here and the plan never listed them** (Langfuse, bucket, `_ro`, spend/keys) — the header
   names their origins.

## F4 — Cadences (core + template; after F1; needs no new table) — ⬜

`defineCadence({ name, touches: [{ name, after: ms, channel, draft(record) }] })`. A schedule tick per cadence: for
each record in the cadence's stage, the next touch is due when the previous touch's `hf_action_log` row is `ok` and
older than `after`; the tick calls `runs.start` with run id `cadence:<name>:<touch>:<record_id>` (a second tick is a
no-op) and the touch run performs one action, key `${cadence}:${touch}`. Never a durable sleep. The key shape is added
to `key-derivation.test.ts`. Demo: a two-touch cadence over the demo notes. `patch`.

**Done means:** `cadence.test.ts` — a tick with nothing due starts nothing; a due record starts exactly one run per
tick; a redeploy mid-touch (redeploy harness) leaves one `hf_action_log` row per touch.

## Risks

1. **Serial migrations with no merge queue** — two chunks racing produce a duplicate `0010`; the additivity test and
   journal baseline catch it, but only after a red `main`. Land migration PRs one at a time.
2. **A channel that declares `dedupes: true` wrongly** re-sends behind the human's back. Telegram: same nonce, same
   message — safe. Lob: the `Idempotency-Key` window is 24 h; a re-entry later than that is a second letter. Mitigation:
   the `uncertain` path stays for rows older than the window. Adversary target (a).
3. **Real money on three new providers** at once. Test keys for Lob; OpenAI and Anthropic under limits set before the
   first call; every key reaches the app only through Coolify's env.
4. **Telegram webhook is a public POST** into `decide()`. The secret header and the link table are the only gates; a
   chat id is not a secret. Adversary target (b).
5. **Documents are the first user-uploaded bytes** — content type, size and the preview's rendering path (never inline
   HTML). Adversary target (c).
6. **Langfuse `environment` on a Hobby project** may be cosmetic if the plan's filters are limited; X6 checks it before
   anything depends on it. Also: tracing currently sends nothing (see L1).
7. **Phase 5 X4/X5 still open** — if the isolation exit finds a shared-state bug, every Phase 6 slice that adds an env
   var or a table inherits it.

**Adversary targets before F2/F3 merge:** (a) every `dedupes: true` declaration against its provider's real idempotency
window and a re-entry after it; (b) the Telegram route — a forged secret, a linked chat whose user was banned since, a
callback for another app's approval id, a replayed nonce; (c) `documents.put` — a `text/html` upload previewed inline, a
5 GB stream, a `storage_key` derived from user input; (d) `profile.get` — a value reaching `hf_llm_call.input`, a Sentry
breadcrumb or the fixture recorder.
