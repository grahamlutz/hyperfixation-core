## Corrections this pass produced

1. **The bot token everywhere a PR is opened** (concern 1). v1 said so ("opened with the bot token so its CI runs");
   Phase 3 dropped the secrets install because nothing read one. Phase 4 is where something does.
2. **`changesets/action` is v2**: inputs are `publish-script`, `github-token`, `push-git-tags`, `create-github-releases`
   (the tooling plan wrote v1's `publish:`). Its README recommends the split sub-actions under trusted publishing.
3. **Publish `pnpm -r pack` tarballs with `npm publish --provenance`**, not `pnpm -r publish`. npm ≥ 11.5.1 is the
   documented OIDC client; whether pnpm 12.4.2's `publish` mints OIDC is unverified (no release note found), and packing
   first is what `release:verify` already checks (`workspaceRangeLeftovers`).
4. **A breaking minor still opens a bump PR.** v1's "a major opens none, with a notice" is superseded by the versioning
   policy: at 0.x the minor is the break, `core-bump.yml`'s `pnpm update --latest` is the only thing that moves the
   template's caret, and the app's suite gates it.
5. **`removeIn` is a minor**, not "the next major" — two-release rule from the policy.
6. **Baseline is the last version commit**, not a tag, for `api-diff` on branches; tags start at `0.1.2`.

> every message. The rest: `ci.yml` had no `permissions:` block and left the per-repo token in

> **Finding — the first OIDC release went through, and the rebuild comparison was never the problem.**
> [run 35513816078](https://github.com/grahamlutz/hyperfixation-core/actions/runs/35513816078) published all nine
> packages from commit `813af20` and pushed tag `v0.1.2`. All nine carry a `slsa.dev/provenance/v1` attestation whose

>
> The reported "integrity mismatch for all nine" does **not** reproduce, and there is no build non-determinism to fix.
> `npm pack`ing `@hyperfixation/eslint-config`, `db` and `core` out of a clean worktree of `813af20` on the maintainer's
> Mac produced tarballs that are **byte-identical** to the ones the ubuntu runner published — same sha512, `diff -r`
> over the extracted trees clean — and `pnpm release:verify 0.1.2` is green for all nine. The builds agree across
> machines because `--frozen-lockfile` pins the whole toolchain (`typescript` 5.9.3, `turbo`, `@types/node` are all

> mtime or a hostname. So no source map, `.d.ts` or `tsbuildinfo` difference exists to chase.
>
> What the episode did expose is that the comparison is the *wrong check* for a CI-published release: it can only ever
> assert that the verifier's machine agrees with the publisher's, so any disagreement — a stale toolchain, the wrong
> commit resolved (the 0.1.1 CLI false positive), a dirty store — reads as though the registry served something it
> should not have. `release:verify` now gates on the attestation instead and keeps the rebuild as a labelled
> informational check: for an attested version a byte difference is a `warnings:` line, and for `0.1.0`/`0.1.1`, which
> have no attestation, it stays the failing check because it is the only evidence there is.
>
> **Three more releases went the same way on 2026-09-20** — `0.1.3`, `0.1.5` and `0.1.6`, each from a merged
> `Version Packages` PR, each attested and tagged by the workflow with nothing done by hand.

> **Finding — the three-minute 404 backoff covers only the document `verify` reads.** The publish and verify steps ask
> for per-version documents, which npmjs serves within about a minute; the bump step's `pnpm update` reads the
> abbreviated packument, which at `0.1.8` was minutes staler still (R1's finding). Anything added here that depends on
> what the registry *serves an installer* needs its own wait — `awaitInstallable` in `registry.ts`, beside
> `awaitVersionDocument` — not this one.

## Operating notes

- **Never `npm publish` by hand.** `.github/workflows/release.yml` publishes on a merged `Version Packages` PR, with
  OIDC trusted publishing configured per package on npm against that workflow. There is no `NPM_TOKEN`.
- **A merged bump is not a deploy.** `hf new` creates Coolify applications with push auto-deploy off, so a merged
  `core-bump/*` PR changes nothing on the box until `hf deploy <name>` runs; `hf doctor`'s version line is what
  catches the gap.
- **IP-restrict every API token** that the box or a laptop holds — the X1 run rolled one after it reached a log.

## Risks

1. Concern 1 is a documented GitHub rule; if an App token also fails to trigger CI (it should not), the fallback is a
   fine-grained PAT with the same two scopes.
2. pnpm 12.4.2 OIDC support unverified — moot with `npm publish` on packed tarballs (correction 3).
3. `changesets/action` v2 may not detect a custom `publish-script`'s published packages for `push-git-tags`; R1 tags
   itself, so nothing depends on it.
4. The template's `minimumReleaseAgeExclude` must still cover `@hyperfixation/*` or the bump PR installs `0.1.1`.
5. `npm install -g npm@latest` in CI is a moving target; pin `npm@11` and bump deliberately.

**Adversary targets before R1 merges:** (a) `release.yml` on a push to `main` that carries no changesets and a version
already on the registry — it must exit 0 with nothing published and no dispatch; (b) the `Version Packages` PR under the
`changeset` job (it deletes changesets — `changeset-check.mjs` says it passes; prove it) and under `api-diff` (versions
change, reports do not); (c) the `id-token` scope — nothing else in the workflow may run with it, and a fork PR must
never reach the publish step.
