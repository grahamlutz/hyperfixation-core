**The one change that matters:** v1 made `DBOS.patch` mandatory for any code change and relied on a workflow surviving, parked in `recv`, across a redeploy. v2 removes both. A run is restartable from scratch at any time because every expensive or side-effecting step is idempotent on an app-level key `(run_id, key)` that does not depend on DBOS step position or code version; DBOS's step checkpoint is a same-version optimisation, never the correctness mechanism. Each deploy is a new immutable `applicationVersion`; `DBOS.patch`, `DBOS.recv`, `DBOS.send`, and `sendInTransaction` are banned from flows by lint. Approvals, the pause gate, and redeploys all use the same primitive: end the workflow, later start a fresh one for the same run.

**Concern to carry into Phase 1:** the restart primitive re-executes app-authored steps that are not ledger/action/approval steps. They must be idempotent (upserts). `@hyperfixation/testing` runs every flow twice by default and fails on any side-effect delta, which catches the common mistake but not every one. This is the honest residual, and it replaces a fatal defect with a testable rule.

**Round 2 added a second rule of the same kind, and one that is not a rule.** The rule: every write a step makes to an app table goes through the step's fenced transaction (`ctx.tx`), which refuses to commit for an attempt that is no longer the run's `current_workflow_id`. Not a rule: the worker now holds its advisory lock until the kernel closes the socket at `process.exit`, which is called on the line after `DBOS.shutdown` returns — so no old-version JavaScript can run once a new worker holds the lock. That half is mechanism, verified live on the adversary's own harness (see the round-2 evidence table).

**Round 3 turned the fence rule into a mechanism and replaced the budget's two counters with a design that has nothing to roll over.** The worker process has two database handles: a *step pool*, which refuses every non-`SELECT` statement not issued on a client checked out by `ctx.tx` — in production, not only under test, and regardless of async context, so a buffered writer, an event listener, a workflow body, or a helper three imports away is refused the same way — and a *control pool*, not importable by apps, on which core's own predicate-fenced writers (`runs.start`, `decide()`, `reconcile()`, the flow wrapper) run. The budget is a row per calendar month in `hf_budget_period`; a call is reserved against, and later billed to, the month stamped on its own ledger row, so there is no counter to reset, no midnight to straddle, and no month in which a stale reservation from a redeploy can count — the reservation sum only ever sees rows whose `workflow_id` is the live attempt.

## Adversary findings: disposition

**Fixed by name (where in this plan):**

| # | Finding | Fix lives in |
|---|---|---|
| Root | `DBOS.patch` cannot tell "not reached" from "crashed before checkpoint" | *The run model*: `DBOS.patch` is never used; `enablePatching: false`; every deploy is a new `applicationVersion` so no code change ever executes against another version's checkpoints. ESLint bans `DBOS.patch`/`deprecatePatch`. |
| 1 | Parked `recv` cannot survive a patched redeploy; rollback poisons it | *Approvals protocol*: two-workflow pattern — `waitForApproval` ends the workflow; `decide()` starts `${run_id}:${attempt}` fresh. *Pause gate*: same — a paused flow ends, `resume` restarts it. No workflow ever parks in `recv`; `DBOS.recv` is banned from flows. Phase 1 gate `redeploy.test.ts` case 1. |
| 2 | Step-ID shift under patch → two clean unflagged provider calls; leaked reservation; duplicate send | *Ledger protocol*: `hf_llm_call`, `hf_action_log`, `hf_approval` keyed `(run_id, key)` — `key` is app-level (record id, touch name), never `DBOS.stepID`. Immune to any ID shift, and there is no shift anyway (no patching). `input_hash` collision guard. Reservation released by the reconciler for `started` rows on finished runs (round 2 replaced this with a derived reservation and a terminal `abandoned` status — see round-2 finding 3; round 3 scoped the derivation to the live attempt — see round-3 finding 6). Phase 1 gate `redeploy.test.ts` case 2 reproduces the adversary's exact scenario and requires 1,001 calls, 1 flagged. |
| 3a | Sweep re-send with the same idempotency key is inert | *Approvals protocol*: there is no `send`. `decide()` bumps the attempt and enqueues the resume workflow with deterministic id `${run_id}:${attempt}` **inside its own transaction** (round 2 replaced the commit-then-enqueue sequence; see round-2 finding 2). Round 2 also corrected this row's citation: `DBOSClient.enqueue()` conflicts are handled at `system_database.js:3800` (`ON CONFLICT (workflow_uuid) DO UPDATE` touching only `updated_at`/`executor_id`), not the batch path at `:856`; both are no-ops on an existing row, which is why a re-issued enqueue is inert and why a wrongly-computed id would have been silently lost. |
| 3b | Fresh-key re-send cross-delivers to a different approval | Eliminated with `send`: the resume workflow's input is `{ runId, approvalId }`; nothing is consumed FIFO from a topic. |
| 3c | `sendInTransaction` on a missing workflow row silently discards committed decisions | `sendInTransaction` is not used anywhere; no core table has an FK to a DBOS row; the resume workflow reads state from `hf_approval` + app tables, so a deleted or garbage-collected DBOS row loses nothing. `runAdminServer: false` in `startWorker()` closes `/dbos-garbage-collect` and every other unauthenticated admin endpoint regardless. |

**Held items from the adversary pass, relied on or retired:** `sendInTransaction` targets the pinned `dbos` schema and wake-up is transactional on commit — held, but **no longer load-bearing** (v2 does not use it). DBOS step checkpoint happens after the body (`dbos-executor.js:684`/`:768`) — still load-bearing; it is the crash window the `started`-row branch exists for. Recovery and dequeue filter on `executor_id` and `application_version` — now used *deliberately* rather than worked around: an old version's workflows are never touched by a new worker's DBOS recovery; the reconciler handles them at the app level.

**Cost accepted in exchange:** a run restarted after a redeploy or pause re-runs its workflow function from the top; ledger/action/approval steps cost one `SELECT` each, other steps re-execute. A run mid-way through a 1,000-record scoring loop at deploy time restarts and replays 1,000 cached rows in seconds; a run killed inside one provider call re-bills that one call, flagged. The shape's named `waitForApproval` step survives as API, with the documented rule that code before it runs again after the decision.

## Approach

Thinnest end-to-end slice first (Phases 1–3), the stability contract mechanized (Phase 4) before a second app exists (Phase 5), remaining primitives one slice each (Phase 6), then the real app (Phase 7). Everything that cannot be bolted on later is in Phase 1, and after the adversary review that list now starts with **the run model**: `hf_run`, app-level ledger keys, the reconciler, per-deploy versions, and the redeploy gate. Phase 2 owns the money and side-effect protocols on top of it.

**The run model, stated once.** A *run* is one execution of a registered flow against an input, identified by `run_id` (the DBOS workflow id of its first attempt) and recorded in `hf_run`. A run is executed by one or more DBOS workflows in sequence — attempt 1 has workflow id `run_id`, attempt `N ≥ 2` has `${run_id}:${N}` — never two at once. A workflow ends early (status SUCCESS, run status `waiting` or `paused`) when the flow reaches a pending approval or a pause; it is cancelled and re-attempted when a deploy leaves it under a dead `applicationVersion`. Every new attempt runs the flow function from the top with the same input. `failed` is terminal: nothing retries a failed run; running the work again is a new run. **`hf_run.current_workflow_id` is a fencing token.** There is one attempt-bump path (used by `runs.start`, `decide()`, `resume`, and `reconcile()`); it locks the `hf_run` row `FOR UPDATE`, computes the next attempt number in application code, writes it with a compare-and-set on the old `attempt`, and enqueues the new workflow in the same transaction. Every write a step makes to an app table happens inside `ctx.tx`, whose first statement takes `FOR SHARE` on the run's row *and* checks `current_workflow_id` is this attempt's workflow id; a mismatch throws `StaleAttempt` and rolls back. So a bump waits for in-flight fenced writes, and no fenced write commits after a bump. Correctness across attempts comes from three tables keyed `(run_id, key)`: `hf_llm_call`, `hf_action_log`, `hf_approval`. DBOS's own checkpoints make crash recovery *within* an attempt cheap and are otherwise irrelevant to correctness. From this follow the four bans, enforced by ESLint `no-restricted-properties` on `DBOS` in every package and app: `patch`, `deprecatePatch`, `recv`, `send`, `getEvent`, `setEvent`, and `DBOSClient.sendInTransaction`. Long durable sleeps are also banned in flows; time-based waits are schedules that start new runs.

**Two pools, one lock order (round 3).** In the worker process (`HF_PROCESS === 'worker'`) the application database is reached through exactly two `pg` pools built by `startWorker()`. The **step pool** (8 connections) is the only handle step code and app code can reach — it is what the app's `@/db` and every core helper used inside a flow resolve to in the worker — and it enforces the fence at the connection: a statement that is not a pure `SELECT` (classified by `pgsql-ast-parser`; a `WITH` containing DML, `BEGIN`, `COPY`, `SET`, and anything unparseable all count as writes) is refused with `UnfencedWrite` unless the client it runs on is currently checked out by `ctx.tx`. No async context is consulted; a buffered writer, an event listener, a workflow body, or a helper imported from anywhere is refused identically. The **control pool** (2 connections) is not in any package's `exports` map — apps cannot import it — and carries core's own writes whose fence is a predicate rather than a lock: the flow wrapper's status updates (`WHERE current_workflow_id = …`), `runs.start`, `decide()`, `reconcile()`, `pause`/`resume`, `records.archive`. These are **control-plane operations**: each begins with `assertNotInWorkflow()` (`DBOS.isWithinWorkflow()` true → `ControlPlaneInWorkflow`), each transaction opens with `SET LOCAL lock_timeout = '30s'`, and each commits only through the helper that asserts the `COMMIT` command tag (`CommitLost` otherwise). In the web process there is one pool and no fence — web code is never inside a run. **Every transaction that locks more than one of these tables does so in this order:** `hf_run` → `hf_budget_period` → (`hf_llm_call` | `hf_approval` | `hf_action_log`) → other app tables; `reconcile()` never locks a budget row. The order is stated once here and every protocol below follows it.

What the stack change still buys: Node `exports` maps make "apps import only the public API" a resolver error; a `BEFORE DELETE` trigger replaces Django's `pre_delete` signal. What it no longer needs to buy: transactional wake-up — v2 has no wake-up.

What it costs, accepted: no `copier update`; no Django admin; no allauth MFA middleware; and the restart cost above.

Rejected: keeping `waitForApproval` as a parked `recv` with per-deploy versions and a drain — a drain cannot bound a 7-day approval wait, so every deploy would still strand approvals. Rejected: `DBOS.forkWorkflow(id, lastStep, { applicationVersion })` to carry checkpoints across versions — it inherits exactly the ambiguity the adversary reproduced whenever code before `lastStep` changed, and the worker cannot know whether it did. Rejected: keying the ledger on `(workflow_id, function_id)` with per-deploy versions and no patching — sound within a version, but a redeploy-restart would re-bill every completed call because the new attempt has a new workflow id; app-level keys make restart free. Rejected: a monorepo per app; `@workflow/ai`; AI SDK tool approvals (all as in v1). **Rejected in round 2:** per-step `timeoutMS` with `DBOS.stepStatus.timeoutSignal` as the interruption mechanism — the signal is advisory (`step.d.ts:19`), a body that ignores it keeps running, and it fires on a *timer*, not on cancellation, so it neither fences nor bounds the hazard. Rejected: relying on Docker's `SIGKILL` at `stop_grace_period` alone — it would work only if the new worker could not start first, which is exactly what holding the lock until exit guarantees for free. Rejected: keeping `reserved_usd` as a counter with a `released_at` stamp per row — correct, but a second bookkeeping path that can drift; deriving the sum from row status has no release step at all. Rejected: a new `reconcile()` step (2) predicate for the decide-then-crash window — `enqueueInTransaction` removes the window instead of shrinking it. **Rejected in round 3:** see the round-3 disposition.

**Size:** Red; the phases are the split. Each phase gets its own Green/Yellow implementation plan when it starts; this document fixes the contracts between them.

## The ledger protocol (`llm.run`, a step on queue `llm`)

`llm.run({ key, prompt, input, schema? })` — `key` is required, a string unique within the run; core helpers derive it (`score:<record_id>`, `draft:<record_id>`), app code passes it explicitly, and a loop must key by the record, never by position. Inside `DBOS.runStep(…, { retriesAllowed: false })`, every transaction below is a `ctx.tx` (fenced on `hf_run.current_workflow_id`, which is the first lock taken, so the lock order `hf_run → hf_budget_period → hf_llm_call` holds by construction):

1. **The gate, one transaction.** Refuse with `AppPaused` if `hf_app_state.paused` (plain read). `P := to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM')`. `INSERT INTO hf_budget_period (period, budget_usd) SELECT $P, budget_usd FROM hf_app_state ON CONFLICT (period) DO NOTHING`, then `SELECT budget_usd, spent_usd FROM hf_budget_period WHERE period = $P FOR UPDATE` — every gate for the month is now serialized on this row. `INSERT INTO hf_llm_call (run_id, key, workflow_id, period = $P, input_hash, status = 'started', estimated_cost_usd, …) ON CONFLICT (run_id, key) DO NOTHING`, read the row back. Then decide, still inside the transaction:
   - row's `input_hash` differs → throw `LedgerKeyCollision` (a bug: same key, different call; never silently served from cache); rollback.
   - row is `ok` → commit (nothing reserved) and return its stored `output` without calling the provider.
   - row is `error` → commit and throw the stored error (a failed call is not retried by replay; a new run is).
   - row **will reserve** — it is the row just inserted, or it is `started` with another attempt's `workflow_id`, or it is `started` with this attempt's `workflow_id` (DBOS recovery re-ran the step), or it is `abandoned`: compute `reserved := COALESCE(SUM(l.estimated_cost_usd), 0) FROM hf_llm_call l JOIN hf_run r USING (run_id) WHERE l.status = 'started' AND l.period = $P AND l.workflow_id = r.current_workflow_id AND r.status = 'running' AND (l.run_id, l.key) <> ($run_id, $key)` — **only rows a live attempt can still complete count**; if `spent_usd + reserved + estimate > budget_usd` → throw `BudgetExceeded`, rollback (the insert is undone; an `abandoned`/stale row stays as it was). Otherwise, for a pre-existing row: set `possible_double_charge = true` (a previous execution crashed between the provider's response and its checkpoint, or was abandoned), `status = 'started'`, `workflow_id` = this attempt's, `period = $P`. Commit. **The committed `started` row under the current attempt *is* the reservation; nothing else records it, and the re-entry of an old row is budget-checked exactly like a fresh one.**
2. Call the provider through the AI SDK (`generateText` / `generateObject`, `experimental_telemetry` carrying `runId`, `key`, `promptName`, `promptHash`).
3. **Completion, one transaction.** `UPDATE hf_budget_period SET spent_usd = spent_usd + $cost WHERE period = <the row's period, read in step 1>` — the budget row first, matching the gate's lock order — then update the ledger row to `ok` with tokens, cost, output, `trace_id`. The row leaving `started` is what releases its reservation; the cost lands on the period the row reserved in, whatever the clock now says. On provider error: row `error`, no spend, throw. If this transaction throws `StaleAttempt`, the attempt is superseded: the provider call happened, its cost is unrecorded here, and the replaying attempt's flag is the audit trail — the step rethrows and the workflow ends.

Stated property: **at most one extra provider call per crash, always visible** (`possible_double_charge`), across same-version recovery *and* cross-version restart — the key never moves. Not exactly-once. **Reservation property (round 3, replacing round 2's):** the budget gate's reservation is the `SUM` of `started` rows *of the current period whose `workflow_id` is their run's live attempt*, computed under the period row's lock; a row stops reserving at the instant its attempt is bumped (the bump's own transaction changes the predicate's right-hand side) or its run leaves `running`, and it re-enters only through the gate. So a redeploy cannot starve anything (round-3 finding 6), a stale row cannot reach another month (finding 7), and no reservation can enter or leave without the lock (finding 8). Rows leave `started` by exactly one of `ok`, `error`, or `abandoned` (set by `reconcile()` step 4 for any row that is not on a live attempt), and none can be released twice because there is nothing to release. **Period property:** `spent_usd` of period P equals `SUM(cost_usd)` of P's `ok` rows at all times; `reconcile()` reports the difference per period and never corrects it; a call is attributed to the month in which the attempt that completed it passed the gate.

**Actions (`actions.perform({ key, channel, … })`, queue `actions`)** use the same `started`-row pattern on `hf_action_log` keyed `(run_id, key)`; the channel receives `idempotency_key = \`${run_id}:${key}\``, stable across attempts, so a provider with idempotency dedupes a re-send. A channel with no idempotency support throws `ActionUncertain`, the row becomes `uncertain`, and a task for Graham to verify is created, rather than re-sending. **`actions.perform` does not require an approval** — a flow calls it directly whenever it does, and calls it after a `waitForApproval` step whenever it doesn't. The choice is the flow's, made per action type at registration; nothing in the core forces a `hf_approval` row to exist before an action can run. A `started` action row that is not on a live attempt is moved to `uncertain` by `reconcile()` step (4) with a task, the same outcome as a channel without idempotency: the action may or may not have gone out, and a human confirms.

**Pause gate and budget.** The `step` wrapper's pre-step reads `paused`; if set, the run is marked `paused` and the workflow ends (`Suspend`). `pause` sets `hf_app_state.paused` and the `llm`/`actions` queue concurrency to 0; `resume` clears both and runs `reconcile()`, which starts the next attempt of every `paused` run. Scheduled flows check `paused` first and return without starting a run. So queued, running, and approved flows all stop at their next step boundary, and a deploy while paused strands nothing. A month boundary needs no action from anyone: the first gate of the new month creates its row from `hf_app_state.budget_usd`, and an admin edit to a period's `budget_usd` takes effect at the next gate.

## The approvals protocol

`waitForApproval` is a gate a flow opts into, not a mandatory step every flow passes through. A flow calls it only for the action types it chooses to gate — everything else calls `actions.perform` directly and never touches `hf_approval` at all.

**Creation, inside `waitForApproval({ key, type, draft, assignee?, expiresIn? })` in a flow:** step 1 (a `ctx.tx`, so `hf_run` is locked `FOR SHARE` first) inserts `hf_approval (run_id, key, …) ON CONFLICT (run_id, key) DO NOTHING` and reads the row back, so a crash inside the step cannot orphan a second row. If the row is decided, return the decision and continue — this is how the resumed attempt passes through. If pending: step 2 notifies (email link straight to the item; Telegram for Graham) and sets `notified_at` if null; then the run is marked `waiting` and the workflow ends via `Suspend`. Code before `waitForApproval` runs again on the resumed attempt and must be idempotent; `runFlowSync` proves it for every registered flow.

**`approvals.decide({ ids, decision, edits, userId, via, decisionKey })`** — the one function used by the web inbox, Telegram, the admin, `records.archive`, and the reconciler's expiry. It is a **control-plane operation**: `assertNotInWorkflow()` first (`ControlPlaneInWorkflow` from inside any run — round-3 finding 2), then:

> `decide(options)` this line implies. Nothing in `workflows` owns a control pool or a `DBOSClient` — the
> worker's pair is built by `startWorker()` and the web's client by `getClient()` — and the thing that
> *holds* a pair is `defineApp`, which is a later chunk and a different package. So `decide()` is handed
> them, and so are its siblings: `reconcile(pool, dbosClient, options)` and
> `runsStart(pool, dbosClient, flow, input, options?)`. `waitForApproval(options)` is the exception, because
> it runs inside a workflow and reads its handles from the run context. `app.approvals.decide(options)` on a
> `defineApp` app is the bare shape this line describes, with the app supplying the first two arguments.

1. One control-plane transaction on a checked-out `pg` client from the control pool (`enqueueInTransaction` needs a `pg.ClientBase`, `client.d.ts:200`): `BEGIN; SET LOCAL lock_timeout = '30s'`. Read the approvals' `run_id`s without locking, then **lock the runs first** — `SELECT … FROM hf_run WHERE run_id = ANY(…) ORDER BY run_id FOR UPDATE` — and only then `SELECT … FROM hf_approval WHERE id = ANY($1) ORDER BY id FOR UPDATE` (round 3: `hf_run` before `hf_approval`, matching `waitForApproval`; the previous order deadlocked against a step's `INSERT … ON CONFLICT` on the same row). If an approval's `run_id` changed between the unlocked read and the locked one, roll back and retry once.

   > **Built ✅ Done (deviated), b0b6242 — `ApprovalRunMoved`.** The retry is the *whole* `decide()` call in a
   > fresh transaction, once, not a partial resumption of the one that lost the race. There is nothing
   > partial to resume: the tag-asserting commit helper has already issued `ROLLBACK` and released the client
   > with the error on the way out (round-3 finding 5's mechanism), so the second attempt re-does the scout
   > read, both lock statements and everything after. A second `ApprovalRunMoved` propagates — losing that
   > race once is ordinary, twice is not.

2. Any failure rolls back with per-row reasons.

   > **Built ✅ Done (deviated), b0b6242 — `ApprovalBatchRefused`, an error this plan does not name.** The
   > replay rule above is stated per row, which leaves the mixed case undefined: some of the batch's rows
   > carry this `decisionKey` and some do not. That batch is **refused whole**, not partially replayed. A
   > batch is written atomically, so a mixed match cannot be this batch half-applied — it means a *different*

## Deployment shape and budgets

One Hetzner box; Coolify; one Postgres 17 with pgvector, one database and two roles per app; each app a three-service Compose application (one-shot `migrate` → `web` and `worker`, both `depends_on: migrate: condition: service_completed_successfully`); per-app custom-format dumps; a few seconds of downtime per deploy, accepted.

**Version per deploy.** The `Dockerfile` declares `ARG SOURCE_COMMIT` and sets `ENV HF_BUILD_SHA=$SOURCE_COMMIT`; Coolify is expected to supply it (unverified — if it does not, the `ci.yml` build step passes `--build-arg SOURCE_COMMIT=$GITHUB_SHA`, and the `Dockerfile` falls back to `git rev-parse HEAD` in the build stage; `startWorker` refuses to launch on an empty value, so a misconfiguration is loud at first deploy, not silent). Both `web` and `worker` read it: the web's `DBOSClient` enqueues under it, the worker launches under it, `/api/status` reports it.

**Redeploy sequence, as the run model sees it:** Coolify stops the old stack (`worker` gets `SIGTERM`; the handler runs `DBOS.shutdown` with a 60 s drain and then `process.exit` on either settlement — the advisory lock is released by the process dying, never earlier — inside a 90 s `stop_grace_period` whose `SIGKILL` is the last line of defence), `migrate` runs (as the migrator role: core migrations, app migrations, `dbos schema -s dbos -r hf_<app>` — **every deploy**, so an SDK upgrade that adds a system table is granted before the worker that needs it starts — triggers, `hf_grant_ro`), `web` and `worker` start; the new worker checks E001–E006, takes the advisory lock (which the old process's death is the only thing that frees), launches under the new SHA (DBOS recovers nothing — every old workflow is another version's), and `reconcile()` cancels and re-attempts every run left `running` under the old SHA through the bump path, whose `FOR UPDATE` on `hf_run` waits out any statement the dead process had in flight — and whose commit is the instant the dead attempts' `started` rows stop reserving budget. Rollback is the same sequence with an older SHA; there is no marker or checkpoint that a rollback can trip over, because no attempt ever executes against another version's checkpoints.

The web container runs Next.js standalone and never launches DBOS. Langfuse's OTel span processor is registered in `instrumentation.ts` (web) and `startWorker()` (worker). Sentry is initialised in both; its `unhandledRejection` listener is why the worker's SIGTERM handler has no rejection to swallow. The DBOS admin server is off in both.

**Connection budget** (per app; role `CONNECTION LIMIT 25`): web Drizzle/better-auth pool 5, web `DBOSClient` 2, worker step pool 8 + control pool 2 (round 3: the former 10-connection app pool, split), worker DBOS pool + LISTEN 5 + 1, worker advisory-lock connection 1, migrate (transient, migrator role, not counted against the limit) 2 — 24 steady. Four apps ≈ 4 × 24 = 96 plus Metabase 4 × 4 and reserve ≈ 10 → under 200 with room for a fifth. PgBouncer stays rejected.

**Memory budget** (`mem_limit`): web 512 MB, worker 768 MB, migrate 256 MB; infrastructure ≈ 4 GB; four apps → 16 GB box.

## Risks

- **Restart re-executes app steps.** Idempotency is a rule plus a default-on test, not a proof. Mitigation: `runFlowSync` restart mode in every contract suite; core helpers are idempotent by construction; the docs show the pattern once.
- **Two attempts running at once** would double non-ledger side effects. Round 2 replaced the mitigation: the lock is held until process death and the process dies on the line after the drain (mechanism, live-verified), and every step write is fenced on `hf_run.current_workflow_id` — round 3 made that half a mechanism too (the step pool refuses unfenced writes in production). Residual: an app step that performs an *external* side effect other than through `actions.perform` (raw HTTP in a step) is fenced by neither half; the stated rule is that outbound side effects go through `actions.perform`, and Phase 6's fetches are reads.
- **The fence is only as complete as the classifier.** Round 3 closed every async-context and import-path escape by moving enforcement to the connection; what remains is a write that the parser classifies as a read (a writing SQL function behind a `SELECT`). Mitigation: no core function writes; app migrations cannot create functions; adversary target (a).
- **A control-plane write without a predicate fence** would be the new round-2-finding-1: the control pool is not fenced by the step pool's rule. Mitigation: every control-plane `UPDATE hf_run` carries `AND current_workflow_id = …` or `AND attempt = $N`; the control pool is unreachable from app code; adversary target (d).
- **A resume can be lost to a booting worker (found in build, 2026-09-17).** `startWorker()` re-zeroes the
  `llm`/`actions` queues when it boots into a paused app, because `registerQueue` reopens them; the read of
  `hf_app_state.paused` and the write of the concurrency are not atomic, so an admin `resume` landing between
  them leaves the app unpaused with both queues pinned at 0 and its backlog enqueued behind them. Liveness
  only — the pause flag is the correctness half and every dispatched step still suspends at its gate — but
  nothing self-heals it and `/api/status` reports `health: 'ok'` while showing the evidence in two separate
  fields. Undecided; see the note on `@hyperfixation/core` in Phase 1 for the three candidate fixes.
- **`lock_timeout` on the control side is a bound, not a diagnosis.** A control-plane transaction that legitimately waits 30 s on `hf_run` (it should not: fenced writes are short) fails and is retried by its caller; the failure names the run. Residual: the JS-level cycle from round-3 finding 2 is prevented at its only known entry (`assertNotInWorkflow`), and the timeout is the backstop for entries not yet known.
- **Period accounting attributes by gate time, not completion time.** A call that reserves on the 30th and completes on the 1st bills the old month; that is the definition, stated once, and drift per period is exact. Residual: a month whose last hours carry many in-flight calls can close slightly over budget by their real cost minus their estimate; estimates are the bound, as before.
- **`BudgetExceeded` is still terminal.** Round 3 removed the phantom reservations that made it fire falsely; it can still fire truly, and the run dies. Mitigation: `/api/status` shows the current period against budget, and the admin can raise a period's `budget_usd` before resuming work by new runs.
- **`SOURCE_COMMIT` build arg** unverified for Coolify; loud fallback at first deploy.
- **Long flows restart on every deploy.** A multi-hour batch loses only in-flight step bodies, but restarts cost wall time; deploy cadence is Graham's to manage, `hf doctor` shows running runs before a deploy.
- **Session-factor policy is Hyperfixation's own code**, **`@hyperfixation/admin` is a build**, **no skeleton auto-update**, **advisory merge gate**, **bucket-scoped Hetzner keys**, **`mem_limit` under Coolify**, **version drift across packages** — unchanged from v1 with the same mitigations.
